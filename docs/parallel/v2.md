# Parallel Search V2 Plan

## Goal

Keep the correctness of the current root-parallel search, but redesign it so it has a real chance to beat the sequential baseline on heavier searches.

V2 is still root-only parallelism.
It is not recursive parallel alpha-beta.

---

## What V1 Proved

V1 already established the important baseline:

- root-parallel search can return the same best move as sequential search
- root-parallel search can preserve deterministic tie-breaking
- root-parallel search can safely fall back to sequential search when budgets are enabled

So correctness is not the main problem anymore.

The main problem is performance.

From the current benchmark snapshot in `docs/benchmarks/root_parallel.md`:

- v1 is slower in every tested case
- the smallest slowdown is still large
- the parallel version searches more nodes than sequential

That means V2 should focus on reducing overhead and recovering more pruning power.

---

## Main Problems V2 Must Solve

### 1. Too Much Thread Launch Overhead

V1 launches one async task per root move.

That is simple, but expensive.
For small searches, thread setup dominates the actual search work.

### 2. No Root-Level Alpha Sharing

In sequential search, once an early root move produces a strong score, later root moves get a tighter alpha bound.

That helps pruning.

In v1, each root move starts with a wide window, so later moves do extra work.

### 3. Too Many Parallel Searches For Cheap Positions

Opening and endgame positions often do not have enough work to justify parallelism.

V1 still parallelizes them when `parallel_root` is on.

### 4. No Concurrency Control

V1 treats all root moves as separate async tasks.

That is not a good long-term execution model.
We need bounded concurrency.

---

## V2 Design Principles

- keep sequential search as the source of truth
- keep iterative deepening sequential
- keep budgeted search sequential
- parallelize only the expensive part of root search
- do not introduce shared TT or shared cancellation yet
- improve performance in small, understandable steps

---

## Phase 1: Add A Profitability Gate

Before using root-parallel search, require the search to look expensive enough.

Suggested checks:

- `parallel_root == true`
- no `time_limit`
- no `node_limit`
- depth is high enough
- root has enough legal moves

The exact thresholds can be tuned later, but the idea is simple:

- shallow searches should stay sequential
- tiny root move counts should stay sequential
- cheap positions should stay sequential

Why:

- this avoids paying thread overhead where parallelism obviously will not help

---

## Phase 2: Seed Alpha With A Sequential First Move

Search the first ordered root move on the main thread before launching parallel workers.

That first move should establish:

- current best move
- current best score
- an initial alpha bound for the remaining moves

Why:

- the first move is often the best-ordered move already
- sequential alpha-beta gets stronger after it has a good bound
- this recovers some of the pruning power that v1 lost

This is the single most important search-quality upgrade in V2.

---

## Phase 3: Replace One-Task-Per-Move With Bounded Workers

Do not launch one async task for every root move.

Instead:

- choose a bounded worker count
- start only that many workers
- let workers pull the next unclaimed root move from shared scheduling state until all remaining moves are consumed

Worker count should be based on:

- hardware concurrency
- root move count
- an optional user-configurable cap

Why:

- this reduces thread creation overhead
- this prevents oversubscribing the machine
- this gives a more realistic execution model for heavier searches

Short note:

- V1 launches one async task per remaining root move
- V2 Phase 3 uses a bounded worker team that repeatedly pulls the next root move from shared scheduling state
- the search result model stays the same, but the scheduling model is cheaper and balances uneven root-move cost better

---

## Phase 4: Keep Deterministic Main-Thread Merging

Even after the worker model changes, keep result selection exactly controlled by the main thread.

That means:

- workers only produce root-move results
- the main thread merges stats
- the main thread chooses the best move
- deterministic tie-breaking stays unchanged

Why:

- this keeps V2 easy to debug
- this preserves the behavior guarantees already validated in V1

---

## Phase 5: Keep Current Search Semantics Intact

V2 should not weaken the safety rules already established in V1.

Still preserve:

- iterative deepening remains sequential
- budgeted searches remain sequential
- recursive alpha-beta remains single-threaded
- per-worker local TT remains the only TT model

Why:

- V2 is a performance cleanup, not a semantic redesign
- shared-budget parallel search and shared TT are separate problems

---

## Phase 6: Add Tuning Knobs

V2 should be benchmarkable and tunable without code changes each time.

Useful knobs:

- maximum parallel workers
- minimum depth required for parallel search
- minimum root move count required for parallel search

These can live in `SearchOptions`, benchmark flags, or both.

Why:

- the best settings are workload-dependent
- you want to benchmark policy, not hard-code guesses forever

---

## Phase 7: Re-Benchmark V2 Against Both Baselines

After implementation, benchmark:

- sequential baseline
- current v1 root-parallel design
- v2 root-parallel design

Use the same scenario matrix as before:

- opening
- midgame
- endgame
- depth 4
- depth 5
- optionally one deeper midgame case

Compare:

- elapsed time
- nodes searched
- nodes per second
- TT hits
- beta cutoffs
- best move and score

Why:

- V2 is only worth keeping if it materially closes the gap or wins on expensive positions

---

## Phase 8: Decide Whether V2 Is Enough

After the re-benchmark, make an explicit call:

- if V2 is competitive or faster on expensive midgame searches, keep iterating on this path
- if V2 is still clearly slower, do not keep stacking small tweaks blindly

If V2 still fails badly, the next real step is a deeper redesign such as:

- principal-variation-first root scheduling
- principal variation splitting
- more advanced worker coordination
- eventually a thread pool

But that should only happen if V2 shows the simple improvements are not enough.

---

## Out Of Scope For V2

Do not include these in V2:

- shared transposition table
- shared atomic stop flags for budgeted parallel search
- recursive multithreaded alpha-beta
- GPU work
- complex lock-free coordination

Those are real future directions, but they make the design much harder very quickly.

---

## Success Criteria

V2 is successful if it does all of the following:

- preserves v1 correctness guarantees
- keeps deterministic root result selection
- stays sequential for budgeted searches
- reduces the performance gap substantially
- ideally becomes competitive or faster on heavier midgame searches

If it only adds complexity and is still far slower than sequential, then it is not a worthwhile stopping point.
