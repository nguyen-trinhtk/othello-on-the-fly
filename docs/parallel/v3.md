# Parallel Search V3 Plan

## Goal

Take the current V2 root-parallel search and make it competitive with the sequential baseline on genuinely heavy searches.

V3 is still root-only parallelism.
It should remain understandable, measurable, and reversible.

---

## What V2 Proved

From `docs/benchmarks/root_parallel_v2.md`:

- V2 is dramatically better than V1
- the profitability gate prevents obviously bad parallel work
- seeded alpha and bounded workers help
- V2 still loses to sequential on the meaningful heavy cases

The biggest clue is this:

- on `midgame depth 5`, V2 searches fewer nodes than sequential, but still takes much longer

That suggests V3 should focus first on lowering parallel overhead, not on deeper search redesign.

---

## Main Problems V3 Must Solve

### 1. Per-Search Worker Setup Is Still Too Expensive

The current parallel path still creates worker threads for each search and still creates fresh worker search state for each root job.

That means V2 avoids some V1 overhead, but not enough.

### 2. Worker State Is Still Too Disposable

Even though V2 uses bounded workers, each evaluated root move still rebuilds isolated search state.

That likely wastes time on:

- transposition-table allocation/setup
- worker context construction
- repeated initialization cost

### 3. The Parallel Gate Is Still Too Coarse

Depth and root-move-count thresholds are useful, but they are only rough guesses.

V3 needs a more workload-aware decision rule.

### 4. Root Coordination Is Still Basic

V2 seeds alpha from the first move once, which is much better than V1.

But after the workers start, they still use only that snapshot.
There is still more pruning to recover at the root level.

---

## Design Principles

- keep sequential as the truth baseline
- keep iterative deepening sequential
- keep budgeted search sequential
- keep worker-side search isolated
- reduce overhead before increasing coordination complexity
- only add complexity when benchmarks justify it

---

## Phase 1: Reuse Per-Worker Search State

Stop rebuilding worker search state for every root move.

Instead:

- each worker thread owns one reusable local `SearchContext`
- each worker thread owns one reusable local TT
- each worker reuses that state across multiple root jobs in the same root search

What should reset between jobs:

- stats that are supposed to be local to one root result
- TT generation for the local table
- any per-job board copy

What should not be rebuilt from scratch every time:

- the worker object itself
- the worker's TT storage
- the worker's scratch search state container

Why:

- this directly attacks one of the most likely remaining overhead sources in V2
- it is simpler and safer than shared TT

---

## Phase 2: Introduce A Persistent Thread Pool

Do not create and join worker threads for every top-level search.

Instead:

- create a small persistent worker pool
- keep it alive across searches
- hand each search a root-work batch
- let idle workers wait for the next batch

Why:

- V2 still pays thread startup and teardown cost every search
- a pool removes that repeated cost
- this is the normal foundation for any more advanced parallel search work later

---

## Phase 3: Tune Concurrency With Real Benchmarks

Once worker setup is cheaper, benchmark different worker caps rather than assuming `hardware_concurrency()` is best.

Compare settings like:

- 1 worker
- 2 workers
- 3 workers
- 4 workers
- auto

Focus on:

- midgame depth 5
- midgame depth 6
- one heavier midgame case if needed

Why:

- alpha-beta does not always scale best at full hardware width
- too many workers can hurt pruning and add coordination cost

---

## Phase 4: Make The Parallel Gate Smarter

Move beyond static depth/move thresholds.

Prefer a gate based on observed search cost, such as:

- previous iterative-deepening layer node count
- previous layer elapsed time
- previous layer root branching size

Good direction:

- only enable root parallelism if the previous completed depth was already expensive enough

Why:

- this makes the gate respond to actual workload instead of just rough shape
- it should parallelize fewer bad cases and more worthwhile ones

---

## Phase 5: Improve Root-Level Coordination

After overhead is reduced, recover more pruning at the root.

Good V3-level directions:

- principal-variation-first root scheduling
- stronger priority for the current best-ordered moves
- possibly limited alpha refresh points between batches

Avoid full shared live-alpha coordination for now.

Why:

- once overhead is lower, search efficiency becomes the next real limiter
- better root coordination is still much cheaper than recursive parallel alpha-beta

---

## Phase 6: Re-Benchmark Against Sequential And V2

After implementation, compare:

- sequential
- current V2
- V3

Use:

- opening, midgame, endgame at depths 4 and 5
- midgame depth 6
- one heavier midgame case if runtime is acceptable

Track:

- elapsed time
- nodes
- TT hits
- beta cutoffs
- nodes per second
- best move and score

Why:

- V3 only matters if it narrows the real gap on heavy searches

---

## What The Current V3 Snapshot Suggests

From `docs/benchmarks/root_parallel_v3.md`:

- the current Phase 5 batching changed the worker-cap story
- `4` workers is the best current parallel setting
- the heavy cases still regressed badly relative to both sequential and saved V2

That means the next work should focus less on "should we parallelize?" and more on "why is the current parallel path still paying so much orchestration cost?"

The most likely issues now are:

- worker state is still recreated at batch boundaries
- Phase 5 introduces more batch barriers and wake/sleep cycles
- the current seeding is still weak for later root batches

So the next phases below are the most likely follow-on improvements if the goal is to keep pushing V3 rather than stopping here.

---

## Phase 7: Persist Worker State Inside The Pool

Right now the thread pool persists, but the worker-owned search state is still rebuilt per submitted batch.

Instead:

- give each pool thread one persistent `ParallelRootWorkerState`
- create those worker states when the pool is constructed
- reuse them across batches and across searches
- reset only the per-job fields before each root move evaluation

Do not keep rebuilding per batch:

- worker-local TT storage
- worker-local `SearchContext` container
- worker-local board scratch object

Why:

- this is the clearest remaining setup cost in the current implementation
- Phase 5 increased batch count, so per-batch worker-state rebuilds now hurt even more
- this keeps the worker model isolated without paying the same construction cost repeatedly

Expected outcome:

- lower batch overhead
- better benefit from the existing thread pool
- a cleaner foundation for trying different batch strategies later

---

## Phase 8: Reduce Batch Barrier Frequency

The current Phase 5 design refreshes `alpha` between batches, but every batch also means:

- another submission into the pool
- another set of worker wakeups
- another synchronization barrier
- another results buffer lifecycle

Instead of always using `batch_size == worker_count`, try coarser batches such as:

- `2 * worker_count`
- `3 * worker_count`
- a small capped range like `min(remaining_moves, max(4, 2 * worker_count))`

Why:

- more frequent alpha refresh can help pruning
- but too many refresh points can cost more than the saved nodes are worth
- coarser batches are the simplest way to trade a little pruning freshness for much lower orchestration cost

Expected outcome:

- less synchronization overhead
- fewer pool round-trips
- a better balance between pruning quality and scheduling cost

---

## Phase 9: Strengthen The Sequential Seed

Right now the parallel path only seeds from the first ordered root move before launching batches.

Try a stronger seed:

- search the first 2 root moves sequentially before launching parallel work
- optionally search the first move full-window and the second move with the current root alpha
- start parallel batches only after that stronger lower bound is known

Why:

- if move ordering is decent, the first few root moves carry most of the pruning value
- a stronger seed can reduce wasted work in every later batch
- this is much simpler than live shared-alpha coordination

Expected outcome:

- fewer explored nodes in later parallel batches
- better root pruning without a major redesign

---

## Phase 10: Try Root-Level PVS Or Null-Window Follow-Ups

If overhead is lower and stronger seeding still is not enough, improve the root-search algorithm itself.

Good next experiment:

- principal-variation-first root handling
- search the best-ordered move full-window
- search later moves with a narrow or null window first
- only re-search full-window when the narrow search fails high

Why:

- this is a common way to recover pruning efficiency when move ordering is decent
- it attacks duplicated root work more directly than just changing thread counts
- it stays root-only, which keeps the complexity below recursive parallel alpha-beta

Expected outcome:

- fewer full expensive subtree searches
- better pruning on later root moves
- a more realistic chance of making parallel competitive on the heavy midgame cases

---

## Phase 11: Re-Benchmark Parallel-Only Tuning

After each of the phases above, re-run the focused heavy-case sweep before touching defaults.

At minimum compare:

- midgame depth 5
- midgame depth 6
- worker caps `1` through `8`
- at least one batch-size variant if Phase 8 lands

Track:

- elapsed time
- nodes
- nodes per second
- TT hits
- beta cutoffs

Why:

- the current V3 work already showed that worker-count behavior can change dramatically after one coordination change
- each follow-on phase should be measured on its own before combining too many ideas
- this keeps the tuning grounded in evidence instead of intuition

---

## Why Not Shared TT Across All Workers Yet

Shared TT is tempting, but it should not be the next step.

Why not yet:

- it adds synchronization or race-tolerant design questions immediately
- lock contention can erase the benefit
- replacement policy gets more complicated under concurrent writers
- bugs become much harder to reason about
- it is harder to tell whether a speedup or slowdown came from better reuse or worse contention

Most importantly:

- V2 is still losing mostly on overhead
- shared TT is not the cleanest way to solve overhead first

When you are ready:

- worker-local reuse is already in place
- a persistent thread pool already exists
- benchmarks show root-parallel overhead is much lower than it is now
- root-only V3 is close to sequential but still losing because workers do duplicated search work
- you are ready to profile contention, not just elapsed time

At that point, shared TT becomes a reasonable experiment instead of a premature complexity spike.

---

## Why Not Recursive Parallel Alpha-Beta Yet

Recursive parallel alpha-beta is a much bigger redesign than it sounds.

Why not yet:

- task explosion becomes easy
- pruning quality can get worse fast if parallelism is introduced in the wrong places
- cancellation and budget handling become much harder
- debugging becomes much harder because the search tree is no longer only root-parallel
- it is much easier to lose correctness confidence

Most importantly:

- root-only parallelism has not yet been made competitive
- if root-only is still clearly behind, deeper recursive parallelism is likely to add complexity before it adds speed

When you are ready:

- V3 root-only search is at least competitive on heavy midgame searches
- you already have a persistent pool and stable worker scheduling
- root-level correctness and determinism are well tested
- you have clear evidence that the remaining bottleneck is below the root, not in setup overhead
- you are prepared to design shared cancellation and budget coordination deliberately

That is the point where recursive parallelism becomes a targeted next step instead of an escalation born from frustration.

---

## Success Criteria

V3 is successful if it does all of the following:

- stays correct against sequential
- stays deterministic at the root
- keeps budgeted search sequential
- lowers the cost of real parallel execution substantially
- becomes closer to sequential on heavy midgame searches
- ideally reaches parity or a real win on at least one heavy case

If V3 still loses badly after overhead reduction, that is the right time to consider shared TT or deeper parallel search.
